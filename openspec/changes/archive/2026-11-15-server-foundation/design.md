# Design

## Context

Workspace with `packages/schema` and `packages/cli`, TypeScript source consumed directly, vitest at the root. See proposal.md for scope.

## Goals / Non-Goals

**Goals:**
- `buildApp(config)` factory that tests use with `app.inject()` and a temporary `DATA_DIR`.
- One process, one SQLite file, no external services.

**Non-Goals:**
- Horizontal scaling or multiple instances on one volume.
- Backups (the volume is the backup unit of the platform).

## Decisions

### Runtime: Node 22+ running TypeScript compiled by esbuild
The server is bundled with esbuild into `dist/server.js` (like the CLI), keeping `@prisma/*` and `better-sqlite3` external because they ship native code and generated files. Dev runs with `tsx watch`. Alternative: run TypeScript via Node type stripping. Rejected: TSX (JSX) is not supported by type stripping.

### Prisma 7 with the better-sqlite3 driver adapter
Prisma 7 uses the `prisma-client` generator with an explicit output (`src/generated/prisma`, git-ignored, generated on install and build) and driver adapters. `@prisma/adapter-better-sqlite3` keeps everything in-process. Migrations live in `apps/server/prisma/migrations` and are committed.

### Migrations applied in-process at startup
Instead of shelling out to `prisma migrate deploy` (which needs the Prisma CLI in the image), the server applies migration SQL files itself: it keeps a `_patchnotes_migrations` table, runs each unapplied `migration.sql` in order inside a transaction, and records it. Migrations are still authored with `prisma migrate dev`. This keeps the production image free of the Prisma CLI and makes tests use exactly the startup path.
Alternative: `prisma migrate deploy` in the container entrypoint. Rejected: larger image, two startup paths (tests vs container).

### Rendering: `@kitajs/html` with a `Layout` component
Components return strings; Fastify replies with `text/html`. `@kitajs/html` escapes children by default (`safe` attributes), and `@kitajs/ts-html-plugin` with `xss-scan` runs during typecheck to flag unescaped interpolation.

### Assets built into `public/`
`@tailwindcss/cli` compiles `src/styles.css` (with `@source` on `src/**/*.tsx`) to `public/assets/app.css`; the build copies `htmx.org/dist/htmx.min.js` next to it. `@fastify/static` serves `public/assets` under `/assets/` with long cache headers.

### Security headers via an `onSend` hook
A small hook sets CSP `default-src 'self'; img-src 'self' data:; media-src 'self'; style-src 'self'; script-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` and `nosniff` on every response. htmx is configured with `htmx.config.allowEval=false` and `includeIndicatorStyles=false` so it works under this CSP.

### Container
Multi-stage Dockerfile on `node:22-bookworm-slim`: install with pnpm, generate Prisma client, build CSS and bundle, then `pnpm deploy --prod` the server into `/app`. Runs as user `node`, `VOLUME /data`, `HEALTHCHECK` on `/healthz`.

## Risks / Trade-offs

- [Own migration runner diverges from Prisma's semantics] → Only forward migrations, same SQL files, same order; covered by a restart test.
- [Native `better-sqlite3` build] → Built in the Docker build stage on the target platform.

## Implementation Notes

- Bundling: everything except native `better-sqlite3` is bundled into `dist/server.js`; only `better-sqlite3` is a runtime dependency. Keeping `@prisma/client` external pulled the Prisma CLI, Studio and TypeScript into the image as peer dependencies (843MB vs 356MB).
- Prisma is pinned to 7.9.0: the `prisma` CLI 7.10.x was published without provenance and pnpm's supply-chain check rejects it as a trust downgrade.
- `apps/server` pins `typescript@5` because `@kitajs/ts-html-plugin` (`xss-scan`, part of `typecheck`) needs the TypeScript 5 compiler API; the rest of the workspace uses TypeScript 7.
- The Prisma client is generated by the root `postinstall`, so `pnpm deploy --prod` of the server does not need the Prisma CLI.
